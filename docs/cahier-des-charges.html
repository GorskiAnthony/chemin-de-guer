01

Présentation du projet

Chemin de Guer (guer : converti, en hébreu) est un blog personnel qui documente un parcours de conversion au judaïsme. Le terme désigne directement la démarche racontée, plutôt qu'un simple jeu de mots.

Le projet s'inspire, sans le reproduire, de sites existants sur le même sujet comme maconversionaujudaisme.com. Il poursuit trois objectifs distincts :

  • Éditorial : offrir un espace de publication durable pour partager ce témoignage et les étapes du parcours.
  • Pédagogique : servir de terrain d'apprentissage complet à Spring Boot 4 et Angular 22, de la conception à la mise en production, sécurité et tests inclus.
  • Communautaire : être publié en open source une fois le socle fonctionnel stabilisé, pour être rejoué, critiqué ou réutilisé par d'autres développeurs.
02

Public cible

Deux publics distincts, aux attentes différentes :

  • Lecteurs du blog : personnes concernées ou intéressées par un parcours de conversion, la pratique juive au quotidien, ou le judaïsme plus largement. Public francophone en priorité.
  • Contributeurs potentiels : développeurs curieux du code source une fois le dépôt ouvert, intéressés par la stack technique ou par le sujet du projet.

04

Spécifications techniques

Architecture

Mono-repo unique contenant un dossier backend/ (API REST), un dossier frontend/ (application cliente) et un docker-compose.yml orchestrant base de données, API et client pour le développement comme pour la production.

Stack retenue

Backend

  • Java21 LTS
  • Spring Boot4.0
  • Spring Data JPA
  • Spring Security
  • PostgreSQL16
  • Maven

Frontend

  • Angular22
  • Standalone components
  • Signals
  • SCSS

Infrastructure

  • Docker
  • Docker Compose
  • VPS Linux

Modèle de données (vue haut niveau)

Entités principales

Tagid, nom, slug
Commentaireid, article associé, auteur, contenu, statut de modération, date
Utilisateurid, email, mot de passe haché, rôle

Authentification

Back-office protégé par une authentification unique (un seul rôle administrateur dans un premier temps, le porteur du projet étant l'unique auteur). Le mécanisme précis (session Spring Security ou JWT) reste à trancher au moment de l'implémentation.

Déploiement

Développement local via Docker Compose. Mise en production sur un VPS Linux (OVH, Hetzner ou Scaleway), accessible dans un premier temps directement par son adresse IP en HTTP, faute de nom de domaine. Un reverse proxy (Traefik ou nginx) avec certificat HTTPS via Let's Encrypt sera mis en place dès l'acquisition d'un nom de domaine.

05

Exigences non fonctionnelles

Sécurité

Protection contre les vulnérabilités courantes (injection, XSS, CSRF), hachage des mots de passe, validation systématique des entrées utilisateur, limitation du débit sur les points d'entrée sensibles (connexion, dépôt de commentaire).

Performance

Chargement de la page d'accueil en moins de deux secondes sur une connexion standard. Pagination des listes d'articles et de commentaires.

Accessibilité

Respect des bases du niveau AA des WCAG : contrastes suffisants, navigation au clavier, alternatives textuelles sur les images.

Compatibilité

Support des deux dernières versions majeures de Chrome, Firefox, Safari et Edge. Affichage responsive sur mobile, tablette et ordinateur.

Qualité et tests

Couverture de tests sur la logique métier critique (authentification, cycle de vie d'un article, fermeture pendant Shabbat) et tests d'intégration sur les points d'entrée de l'API.

06

Fermeture automatique pendant Shabbat

Fonctionnalité distinctive du projet : le site se ferme de lui-même pendant le Shabbat, sans intervention manuelle.

Spécification

Objectif : pendant la fenêtre du Shabbat, toutes les routes publiques affichent une page dédiée ("fermé pour Shabbat, retour après Havdala") à la place du contenu habituel.

Calcul des horaires : les heures d'entrée (allumage des bougies) et de sortie (Havdala) sont récupérées via une API de type Hebcal, pour une ville de référence à définir.

Marge de sécurité : une marge configurable peut être appliquée avant l'heure officielle d'entrée du Shabbat.

Le contenu redevient accessible automatiquement à la sortie du Shabbat, sans action manuelle du porteur du projet.

07

Direction artistique

Palette inspirée des couleurs du drapeau israélien (bleu profond, blanc, touche dorée ou sable), pour une ambiance vivante et chaleureuse, à l'opposé d'un minimalisme froid.

Les maquettes détaillées sont disponibles dans le système de design.

08

Gouvernance et open source

Le code source sera publié en open source une fois le socle fonctionnel stabilisé. Le dépôt dispose déjà de modèles d'issues (bug, fonctionnalité) et de pull request pour cadrer les contributions futures.

Convention de commit : messages rédigés en français, sans tiret cadratin, sans aucune attribution à un outil d'intelligence artificielle.

Licence : Apache 2.0. Choisie pour sa protection explicite contre les brevets, en plus des permissions courantes de réutilisation et de modification.
09

Répartition des rôles

L'intégralité du code applicatif (backend et frontend) est écrite par le porteur du projet, dans une démarche d'apprentissage assumée. Toute assistance extérieure, y compris par intelligence artificielle, se limite à la revue : sécurité, performance et tests. Aucune ligne de code applicatif n'est produite par un tiers.

11

Critères de validation de la V1

  • Un visiteur peut consulter, filtrer par tag et rechercher des articles publiés.
  • Un administrateur authentifié peut créer, modifier, publier et supprimer un article.
  • Un visiteur peut commenter un article, le commentaire passant par une étape de modération.
  • Le site devient inaccessible publiquement pendant la fenêtre de Shabbat calculée automatiquement, et redevient accessible de lui-même ensuite.
  • Le site est déployé et accessible sur le VPS de production.
  • Aucune faille de sécurité critique n'est identifiée lors de la revue.
12

Points ouverts

Décisions restant à prendre avant ou pendant le développement :

  • Ville de référence utilisée pour le calcul des horaires de Shabbat.
  • Mécanisme d'authentification définitif pour le back-office (session ou JWT).
  • Choix définitif du nom de domaine et de l'hébergeur VPS.

Document de cadrage destiné à être présenté et validé avant le début du développement des fonctionnalités. Toute modification de périmètre après validation fera l'objet d'une nouvelle version de ce document.
